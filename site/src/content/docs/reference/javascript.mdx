The `pondra` package is a small client for a node's HTTP API. It has no dependencies and runs on
Node 18 or later, or on any runtime with `fetch`. It is an ES module. `connect` is the one way in: it
reaches a node that is running, or opens a lake and runs its node inside this process. It returns the
connection at once, a `Pondra` (`new Pondra(url, options)` does the same for a node). A query is a
[frame](#frames), with nodejs-polars' names for Python's frames: the same steps send the same SQL text
from both clients.
See [names](/pondra/reference/names/).

```js
import { connect } from "pondra";

const db = connect("http://localhost:8080");
console.log(await db.sql("SELECT 1 AS one"));
```

```text
[ { one: 1 } ]
```

## Connect

| Call | Meaning |
|---|---|
| `connect(target, options)` | the one way in: a connection to the lake or node `target` names, with the three kinds below. It returns at once, and `await db.ready` waits for a lake's node |
| `await binary()` | the path of the `pondra` executable: `$PONDRA_BIN`, or the one npm installed for this platform |

`target` says what to connect to:

- **Nothing, or `":memory:"`** (as DuckDB spells it): a new lake held in this process's memory, gone at `close()`.
- **A folder, or a bucket's URL** (`s3://`, `gs://`, `az://`): that lake. Its node runs in this process (Node, Bun,
  Deno), through the library the package ships, so there is no second process to start. Its SQL may read and write
  files on this machine, and Python's functions and procedures run with a Python here that has the `pondra` package
  (`python: false`: none). The other options are the node's [settings](/pondra/reference/environment/) by name:
  `memory_gb: 2` is `PONDRA_MEMORY_GB`, fixed by the first node a process opens.
- **`http://` or `https://`** (or an array of them, any of a cluster's nodes): a node running somewhere, with the
  options below.

`connect` answers at once. A lake's node opens meanwhile, and the first call waits for it. `await db.ready` waits
for it explicitly, and throws why it didn't open. A process holds one such node at a time: the same lake connected
again is another connection to it, and another lake connected while one is open gets a node of its own beside the
process. `close()` ends the connection; the node stops with the last one, or when the process ends (`process.exit()`
too). `local()` and `open()` still work, with a warning, until 1.0.

A connection to a node takes these options:

| Option | Default | Meaning |
|---|---|---|
| `token` | none | sent as `Authorization: Bearer …`; the token's role decides what the connection may do |
| `user`, `password` | none | sign in as a [user](/pondra/guides/security/#users-roles-and-grants) instead: its name and password (or one of its tokens) |
| `onNotice` | `console.log` | called with each line a procedure printed. `null` keeps them quiet |
| `retrySecs` | 60 | how long a call keeps trying while no node answers it (0: once) |
| `ca` | none | a PEM file of the authority that signs an `https` node's certificate. This process trusts it from the first request, as `NODE_EXTRA_CA_CERTS` would. Node 22.19 or later has the call for it; older Nodes throw, naming the two ways round it |
| `fetch` | the global `fetch` | a function used in place of it, for TLS of your own (Bun's, an undici `Agent`, Deno's client). It brings its own certificates, so `ca` doesn't apply to it |

A lake takes these options, with its folder or bucket:

| Option | Default | Meaning |
|---|---|---|
| `token` | none | sent with the requests, as for a node |
| `python` | `true` | give the node a Python, for Python functions and procedures, if this machine has one with the `pondra` package (`--python auto`); `false` for none |
| `port` | a free port | the port the node listens on (`127.0.0.1`), for the console and other programs; `db.url` is where it is once `db.ready` |
| `onNotice` | `console.log` | called with each line a procedure printed. `null` keeps them quiet |
| any setting, by name | none | `memory_gb: 2` is `PONDRA_MEMORY_GB`: the node's [settings](/pondra/reference/environment/), fixed by the first node a process opens; a misspelt one is refused, naming the nearest |

Given a cluster's nodes, a connection rides out one going away, as the
[Python client](/pondra/reference/python/#connect) does: a call no node ran goes to the next node,
and so does one that can't be applied twice (a query, `append`, a single `INSERT`, `UPDATE`,
`DELETE` or `MERGE`, sent with a job). While a node holds the session (a transaction, temporary
tables, settings, variables), calls go to it alone; if it goes, the next call fails with `sqlstate`
`08006`.

```js norun
const db = connect(["http://10.0.0.1:8080", "http://10.0.0.2:8080", "http://10.0.0.3:8080"]);
```

Because this program started the node, its SQL may read and write files on this machine
(`SELECT * FROM read_csv('jan.csv')`). A node beside this process writes its standard error to `pondra-<port>.log`
in the temp folder: one that doesn't start throws `the node didn't start; its log: <path>`, and the log says why.

```js
import { connect } from "pondra";

const db = connect("scratch", { memory_gb: 2 });
console.log(await db.sql("SELECT 1 AS one"));
await db.close();
```

## Queries

| Method | Returns |
|---|---|
| `await db.sql(query, params)` | a query's rows, as an array of objects: `db.sql(query)` is a [frame](#frames), and awaiting it runs it. Other statements (`CREATE`, `INSERT`, `UPDATE`, `DELETE`, `CALL`, several at once) run at once, and awaiting them gives the last one's outcome. `params` gives values for `$name` in the query |
| `await db.run(file, params = {})` | a `.sql` file on this machine, or else a `.sql`, `.py` or notebook file of the lake's, run on the node ([Run files as jobs](/pondra/guides/workspace/)); or SQL text. `$name` takes `params.name` |
| `await db.find(text, { kind })` | every object, part and concept whose name, comment or definition has each word of `text`, best first: the rows of [`pondra.find`](/pondra/sql/system-tables/#parts-and-finding-things). `kind: "column"` searches one kind |

A parameter is a JSON value: a number, string, boolean, `null` or an array.

| Method | Returns |
|---|---|
| `await db.vars()` | this connection's SQL variables (`DECLARE $day …`, `$day = …`: [Variables](/pondra/sql/statements/#variables)) as an object of their values |
| `await db.getVariable(name)` | one variable's value, `null` if it has none |
| `await db.setVariable(name, value)` | sets it, as `$name = …` in SQL (the value bound, never pasted in) |
| `await db.resetVariable(name)` | forgets it (`RESET VARIABLE name`) |
| `await db.parameters(file)` | a file of the lake's parameters: each `DECLARE PARAMETER`'s name, type, default and comment, and each `$name` it needs |

```js
import { connect } from "pondra";

const db = connect("http://localhost:8080");
await db.sql("DECLARE $since DATE = DATE '2026-09-01'");
await db.setVariable("top", 2);
console.log(await db.vars());
console.log(await db.sql("SELECT $since + 1 AS next, $top * 10 AS t"));
```

```text
{ since: '2026-09-01', top: 2 }
[ { next: '2026-09-02', t: 20 } ]
```

```js
import { connect } from "pondra";

const db = connect("http://localhost:8080");
await db.sql("CREATE TABLE orders (id BIGINT, item VARCHAR, amount DOUBLE)");
console.log(await db.append("orders", [{ id: 1, item: "tea", amount: 7.0 }, { id: 2, item: "cake", amount: 4.5 }]));
console.log(await db.sql("SELECT item, sum(amount) AS total FROM orders WHERE amount > $min GROUP BY item ORDER BY item", { min: 1 }));
console.log(await db.run("SELECT $x + 1 AS y", { x: 41 }));
```

```text
{ seg: 1, duplicate: false, conflict: false, row: 0, ms: 0, block: 0 }
[ { item: 'cake', total: 4.5 }, { item: 'tea', total: 7 } ]
[ { y: 42 } ]
```

A null is left out of its row. `SELECT NULL AS x, 1 AS y` gives an object with no `x` key.

```js
import { connect } from "pondra";

const db = connect("http://localhost:8080");
console.log(await db.sql("SELECT NULL AS x, 1 AS y"));
```

```text
[ { y: 1 } ]
```

<Aside type="caution">
Read a missing key as `null`: `row.x ?? null`. This client doesn't put the nulls back, as the
[Python client](/pondra/reference/python/#writing-rows) does.
</Aside>

## Writing rows

| Method | Returns |
|---|---|
| `await db.append(table, rows)` | appends an array of objects exactly once: a retry after a lost answer is recognised and not applied twice. Answers with `{ seg, duplicate, conflict, row, ms, block }`, as the [Python client](/pondra/reference/python/#writing-rows) explains them. A node that is down, or turns the request away before running it, hands the append to the next node, for up to `retrySecs`. Any other refusal, such as `23514` for a CHECK, is thrown at once |
| `await db.lookup(table, key)` | the current row of one key of a keyed table, or `null` |

Other writes are SQL: `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `COPY`.

```js
import { connect } from "pondra";

const db = connect("http://localhost:8080");
await db.sql("CREATE TABLE users (id BIGINT PRIMARY KEY, name VARCHAR)");
await db.append("users", [{ id: 7, name: "ann" }]);
console.log(await db.lookup("users", 7), await db.lookup("users", 8));
```

```text
{ id: 7, name: 'ann' } null
```

## Frames

A frame is a query that hasn't run yet, built a step at a time with nodejs-polars' names for
[Python's frames](/pondra/reference/frames/) (`withColumns`, `groupBy`, `isNull`, `nUnique`,
`joinAsof`). Each step is a CTE of one SQL statement (`await frame.sql()` shows it), which awaiting the
frame sends to the node: the same plan, speed and answer as the SQL. The same pipeline written in
Python and in JavaScript sends the same SQL text.

| Method | Returns |
|---|---|
| `db.table(name)`, `db.sql(query)` | a table or a view, or a query, as a frame |
| `db.readParquet(source, options)`, `db.readCsv`, `db.readJson`, `db.readNdjson`, `db.readDelta`, `db.readIceberg` | files as a frame, read where the node runs each time the frame runs: a path, a URL (`s3://`, `gs://`, `az://`, `https://`), a folder, a glob or a list of them. Options take Polars' names (`hasHeader`, `separator`, `hivePartitioning`, `snapshotId`) or SQL's `read_*` ones (`header`, `delim`) |
| `await db.writeTable(name, data, { mode = "create" })` | rows into a table: a frame, a query's SQL text, or an array of row objects. `mode`: `"create"` (an error if the table is there), `"append"` or `"overwrite"`. An array's values make the new table's columns, and its rows are appended exactly once |

A frame's steps (`filter`, `select`, `withColumns`, `groupBy(…).agg(…)`, `join`, `sort`, `limit`,
`unique`, …) and its sinks (`writeTable`, `writeParquet`, `toView`, `show`, `item`, `toArrow`) are
those of the [Python frames](/pondra/reference/frames/), named as nodejs-polars names them. `col`,
`lit`, `when`, `sum`, `count` and the other expressions are imported from `pondra`.

```js
import { connect, col } from "pondra";

const db = connect("http://localhost:8080");
const totals = db.table("orders").groupBy("item").agg(col("amount").sum().alias("total")).sort("item");
console.log(await totals);
console.log(await db.table("orders").filter(col("amount").gt(5)).select("item"));
await db.writeTable("totals", totals);
await db.writeTable("notes", [{ id: 1, text: "first" }]);
console.log(await db.sql("SELECT count(*) AS n FROM totals JOIN notes ON true").item());
```

```text
[ { item: 'cake', total: 4.5 }, { item: 'tea', total: 7 } ]
[ { item: 'tea' } ]
2
```

## Transactions

`await db.transaction(async (tx) => { … })` runs the block's statements as one commit (`BEGIN`, the
block, `COMMIT`). The block reads its own writes. If it throws, the transaction is rolled back and
the error goes on to the caller. Another commit that changed one of its rows first refuses it, with
`sqlstate` `40001`: run the block again. It answers what the block returns.

```js
import { connect } from "pondra";

const db = connect("http://localhost:8080");
await db.sql("CREATE TABLE ledger (id BIGINT, amount DOUBLE)");
const total = await db.transaction(async (tx) => {
  await tx.sql("INSERT INTO ledger VALUES (1, 5.0), (2, 2.5)");
  return (await tx.sql("SELECT sum(amount) AS total FROM ledger"))[0].total; // its own writes
});
console.log(total);
try {
  await db.transaction(async (tx) => {
    await tx.sql("INSERT INTO ledger VALUES (3, 9.0)");
    throw new Error("the check failed");
  });
} catch (e) {
  console.log(e.message); // rolled back: id 3 isn't there
}
console.log(await db.sql("SELECT count(*) AS n FROM ledger"));
```

```text
7.5
the check failed
[ { n: 2 } ]
```

## Procedures

| Method | Returns |
|---|---|
| `await db.call(name, ...args)` | `CALL name(…)`: its rows or outcome. What the procedure printed is in `db.notices`, and goes to `onNotice` |
| `await db.start(name, ...args)` | starts the procedure on the node without waiting, and answers the run's id. Its row in `pondra.runs` says how it went |
| `await db.callProcedure(name, ...args)` | the name `call` had up to 0.22: the same method |
| `await db.task(name, sql, { schedule, after, when, retries, retryDelay, timeout, onFailure })` | [`CREATE TASK`](/pondra/sql/statements/#functions-procedures-and-tasks): `sql` run on a `schedule`, or `after` other tasks |
| `await db.executeTask(name, values)` | `EXECUTE TASK`: its graph runs now, with these values for its tasks' `$name`s; answers with the run's id |
| `await db.wait(id)` | waits for a run (`start`'s or `executeTask`'s) to end, as SQL's `AWAIT 'id'`; throws its error if it failed |
| `await db.createFunction(name, { params, returns, language, body, file, entry, vectorized, strict, volatility, packages, timeout, cache, replace })` | `CREATE FUNCTION`: a function called from SQL and from frames. `language: "sql"` takes a SQL body, which names its parameters as they are; `"python"` (the default) runs Python code on the node, as `body` text or a `file` of it, with `entry` naming the function to run. `params` maps each parameter to its SQL type, or to `[type, default]`; `returns` is a SQL type, or an object of columns and their types (a table). `cache: "10 minutes"` reuses an answer that long for the same arguments |
| `await db.createProcedure(name, { params, language, body, file, entry, packages, timeout, replace })` | `CREATE PROCEDURE`, with the options of `createFunction`. A SQL body names its parameters with `$` (`$n`), as a `CALL` binds them |
| `await db.routines()` | this lake's functions and procedures, as an object keyed by name: each one's kind, parameters, language and body |

The arguments are passed by position. A function is called from SQL.

```js
import { connect } from "pondra";

const db = connect("http://localhost:8080");
await db.sql("CREATE PROCEDURE report(day VARCHAR) LANGUAGE sql AS $$ SELECT count(*) AS n, $day AS day FROM orders; $$");
console.log(await db.call("report", "2026-09-27"));
const run = await db.start("report", "2026-09-28");
await db.wait(run);
console.log(await db.sql(`SELECT routine, status FROM pondra.runs WHERE id = '${run}'`));
```

```text
[ { n: 2, day: '2026-09-27' } ]
[ { routine: 'report', status: 'ok' } ]
```

Python's `@db.function` and `@db.procedure` take a Python function from Python's own source.
JavaScript sends its code as text or as a file, through `createFunction` and `createProcedure`.

```js
import { connect } from "pondra";

const db = connect("http://localhost:8080");
await db.createFunction("twice", { params: { x: "INT" }, returns: "INT", language: "sql", body: "SELECT x * 2" });
await db.sql("CREATE TABLE doubled (a INT)");
await db.createProcedure("add_row", { params: { n: "INT" }, language: "sql", body: "INSERT INTO doubled VALUES ($n)" });
await db.call("add_row", 21);
console.log(await db.sql("SELECT twice(a) AS v FROM doubled"));
console.log(Object.keys(await db.routines()).includes("twice"));
```

```text
[ { v: 42 } ]
true
```

## Views

`await db.view(name, query, { materialized, temporary, replace = true, ...options })` makes a view
others read by name, from SQL or a frame. It resolves to the node's answer for the `CREATE`, such as
`{ view: 'big_orders' }`; a refusal rejects there, naming what the node refused. `db.table(name)`
reads it as a frame.

| Option | Meaning |
|---|---|
| `materialized: true` | keep it up to date with each new row (`CREATE MATERIALIZED VIEW`) instead of running the query when it is read |
| `temporary: true` | a temporary view (`CREATE OR REPLACE TEMP VIEW`): this connection's alone, gone when it closes. A materialized view can't be one |
| `replace` | for a stored view, `false` refuses to replace one that exists |
| other options | the options of a materialized view: `window`, `size_secs`, `slide_secs`, `lateness_secs`, `session`, `gap_secs`, `join`, `time`, `within_secs`. They need `materialized: true`. See [table options](/pondra/sql/table-options/#materialized-views) |

```js
import { connect } from "pondra";

const db = connect("http://localhost:8080");
console.log(await db.view("big_orders", "SELECT * FROM orders WHERE amount > 5"));
console.log(await db.view("spend", "SELECT item, sum(amount) AS total FROM orders GROUP BY item", { materialized: true }));
```

```text
{ view: 'big_orders' }
{ view: 'spend', materialized: true }
```

## Following changes

| Method | Yields |
|---|---|
| `db.watch(table, { after, changes })` | an async generator of a table's new rows as they commit, one object each. For a keyed table, every upsert and delete. `after` replays from that position first. `changes: true` also yields UPDATE's and DELETE's rows, each with `_change_type`, `_row_id` and `_version` |
| `db.live(sql, { params, everyMs })` | an async generator of a query's answer now, and again each time a commit changes it: an array of rows each time. An answer that comes out the same isn't sent again. A busy table is queried at most every `everyMs` (default 100) |

`db.position` is where the stream has got to: a `live` answer sets it, and so does each batch of
`watch`, which the node marks. A `watch` sets it when its next row is asked for, so read one row past
a batch before reading it: `db.watch(table, { after: db.position })` then yields what came after.
With no `after` (or `after: null`) a watch starts from now: only the rows committed from then on.
Both run until you leave the loop: a `break` ends the stream on the node.

```js
import { connect } from "pondra";

const db = connect("http://localhost:8080");
for await (const row of db.watch("orders", { after: 0 })) {
  console.log(row);
  break;
}
for await (const rows of db.live("SELECT count(*) AS n FROM orders")) {
  console.log(rows);
  break;
}
```

```text
{ id: 1, item: 'tea', amount: 7 }
[ { n: 2 } ]
```

## Members

| Member | Meaning |
|---|---|
| `db.url`, `db.urls` | the node in use (the first, to begin with), and every node the connection was given |
| `db.token` | the token in use |
| `db.held` | the node holding this connection's session, while one does (a transaction, temporary tables, settings, variables); `null` otherwise |
| `db.notices` | what the last statement's procedures printed, as an array of strings |
| `db.onNotice` | the function each notice goes to |
| `db.producer`, `db.seq` | the name `append` writes under, and its last sequence number |
| `db.session` | this connection's session id: its temporary tables and views, and the variables of its `DO LANGUAGE python` blocks, live under it |
| `db.position` | where the last `live` answer or `watch` batch is as of: a commit, the place to resume from |
| `db.consoleUrl` | the console in a browser, as this connection. A lake's node that `connect()` opened answers only this program, so the link carries its key (`#key=…`) and works while the node runs: keep it to yourself, as a token |
| `await db.request(method, path, body, type)` | one HTTP request to the node, as the methods above make them. Answers the `fetch` response, and throws on an error status with the text `status: message`; the error's `sqlstate` is Postgres's code for it (`23514`, `40001`…) |

The members are read from the connection. `request` is for a path the methods don't cover:

```js
import { connect } from "pondra";

const db = connect("http://localhost:8080");
console.log(db.urls.length, db.producer.startsWith("js-"));
console.log(db.session !== "", db.notices, db.seq, db.held);
await db.setVariable("top", 2);
console.log(await db.getVariable("top"), await db.getVariable("nope"));
await db.resetVariable("top");
console.log(await db.getVariable("top"));
const stats = await db.request("GET", "/stats");
console.log(stats.status);
await db.close();
```

```text
1 true
true [] 0 null
2 null
null
200
```

## Close

`await db.close()` takes no argument. It ends the connection's session, so its temporary tables
and views go, and so do the variables of its `DO LANGUAGE python` blocks. It also stops the lake's
node once no other connection to it is open; a node beside this process gets 15 seconds to stop, then is killed.

```js
import { connect } from "pondra";

const db = connect("http://localhost:8080");
await db.sql("CREATE TEMP TABLE picked AS SELECT * FROM orders WHERE amount > 5");
console.log(await db.sql("SELECT count(*) AS n FROM picked"));
await db.close();
```

```text
[ { n: 1 } ]
```

<Aside type="caution">
`for await` over `watch` or `live` holds a connection to the node until you leave the loop. Always
`break` out of it, or the process stays alive.
</Aside>
