Every number on this page comes from Pondra's own status report and comparison notes, with what was
measured and on what machine. Read them as ratios and shapes: your hardware will give other times.
Where another engine is ahead, the page says so.

## How the numbers were taken

- **The machine:** one 2-vCPU virtual machine with 7 GB of memory (8 GB for the single-node TPC-H runs),
  on local disk, except the latest single-machine numbers (round 32), which ran on 4 cores with 15 GB.
  Where a number says R2, it used a real Cloudflare R2 bucket. Every engine ran alone. Each section
  says which round measured it; Pondra has changed since the older ones.
- **The engines:** Pondra, built on Apache DataFusion 55; Spark 4.2.0 (PySpark,
  `local[*]`); Flink 2.3.0 (PyFlink, a local MiniCluster, parallelism 2); DuckDB 1.5.5; Polars 1.44.2;
  Daft; and Bodo. Each single-node engine ran its own published TPC-H code.
- **Same data, same answers:** every engine read the same data with the same SQL, and the answers were
  checked against DuckDB's, or by row counts where noted.
- **Not run here:** Fluss and Databricks' Lakehouse//RT can't run on this machine. They are compared
  with their published numbers.

## SQL on one machine

### Latest: TPC-H, ClickBench and TPC-DS against DuckDB 1.5 and 2.0's preview

Measured on 2026-10-02 (round 32) on a 4-core machine with 15 GB of memory, so these times don't
compare with the 2-vCPU tables further down. Best of three runs, with
`tools/bench/singlenode.py` (`--suite clickbench` for ClickBench). Every answer was checked against
DuckDB's. DuckDB 2.0 is a preview build (`2.0.0.dev2609250715`); its stable release is 1.5.
Pondra's rows were measured again after round 32's last changes, that evening; DuckDB 1.5.5 over
Parquet, run beside them again, took 2.05 s on TPC-H and 11.10 s on ClickBench.

**TPC-H, scale factor 1** (all 22 queries):

| | From files (Parquet) | From memory |
|---|---|---|
| **Pondra** | 2.16 s | 1.24 s, hot columns |
| DuckDB 1.5.5 | 2.19 s | **1.05 s**, its own tables |
| DuckDB 2.0, preview | 1.98 s | **0.92 s**, its own tables |
| Polars 1.44.2 | 1.92 s | |

**ClickBench, the first 10 million rows of `hits`** (all 43 queries):

| | From files (Parquet) | From memory |
|---|---|---|
| **Pondra** | **10.47 s** | 6.58 s, hot columns |
| DuckDB 1.5.5 | 11.11 s | 7.18 s, its own tables |
| DuckDB 2.0, preview | 10.89 s | **6.22 s**, its own tables |

Seven of ClickBench's answers differ from DuckDB's, and from DuckDB 2.0's to 1.5's too. They are ties
that a `LIMIT` cuts through: `tools/bench/clickbench_ties.py` checks that each has the same row
count, every row is a real group, and the sort key's values are the same.

Reading Parquet, Pondra is level with DuckDB 1.5 on TPC-H and ahead of both DuckDBs on ClickBench.
With the data in memory, Pondra is ahead of DuckDB 1.5's own format on ClickBench and behind it by
about 15% on TPC-H; 2.0's preview is ahead on both. Pondra wins where the work is in the
expressions: ClickBench's regular expression (q29) takes 1.54 s against DuckDB's 3.02 s. Round 32
closed most of the gap where a filter keeps a few rows of many columns: `SELECT *` of a top-N (q24)
took 1.27 s from memory and 2.26 s from files, and now 0.42 s and 0.82 s, since a scan of many
columns under a sort with a `LIMIT` reads the other columns only for the rows its filters keep
(DuckDB's own tables: 0.11 s). Keeping the in-memory columns in allocations of their own lets about
half as much again of a table stay in memory within the same limit.

**TPC-DS, scale factor 1:** all 99 queries give DuckDB's answers (`tools/tpcds_check.py`). From
memory, one run each, they take 12.1 s against DuckDB 1.5's 8.0 s on its own tables.

### TPC-H against DuckDB, Polars, Daft and Bodo (round 12)

All 22 queries at scale factor 1 (SF1: 6 million lineitem rows) and scale factor 10 (SF10: 60 million),
on one 2-vCPU, 8 GB machine. Best of three runs. Pondra read its own lake, loaded with one `INSERT` per
table. The others read the same Parquet files.

**From files, every query** (nothing loaded into memory first):

| | SF1 | SF10 |
|---|---|---|
| **Pondra** (`PONDRA_HOT_GB=0`) | **3.19 s** | **38.0 s** |
| DuckDB 1.5.5 | 3.36 s | 39.8 s |
| Polars 1.44.2, in-memory engine | 3.78 s | query 9 ran out of memory |
| Polars, streaming engine | 3.18 s | 42.8 s |
| Daft | 6.11 s | 89.0 s |

Bodo was run too. Eight of its 21 answers differed from DuckDB's and one query crashed, so its times
aren't a comparison.

**From memory** (the load is not in the times):

| | SF1 | SF10 |
|---|---|---|
| **Pondra**, with hot columns kept decoded (1.5 GB) | 1.96 s | 35.9 s |
| DuckDB, its own tables | **1.80 s** | needs about 7 GB of temporary space beyond this machine's memory: no room |

Reading Parquet, Pondra was the fastest of the five at SF10, and level with Polars' streaming engine at
SF1 (3.19 s against 3.18 s is a tie, not a lead). It is the only one that also ingests, serves and
scales out. DuckDB stays about 9% ahead when both hold the data in memory at SF1. At SF10 DuckDB
couldn't hold it here at all, while Pondra's cache takes what fits and gives it back when queries need
the memory.

A later recheck (round 25, SF1, 2 vCPUs) kept the same standing:

| Engine | Time for all 22 queries |
|---|---|
| Pondra | 2.11 s |
| DuckDB over the same Parquet | 3.45 s |
| **DuckDB in its own format** | **1.65 s** |
| Polars | 3.80 s |
| Daft | 6.98 s |

DuckDB in its own format is still ahead of Pondra. Pondra's ratio to DuckDB over the same Parquet was
0.61, against 0.60 the round before.

### TPC-H against Spark

The 22 queries at SF1 on the same Parquet files, best of two runs (run again on 2026-10-01, round 30,
with `tools/bench/tpch.py`). Pondra's runs went over HTTP and returned JSON, and each run was a new
query, so the result cache never answered. All three engines returned the same row counts for every
query.

| | Pondra | Spark 4.2 (`local[*]`) | DuckDB 1.5.5 |
|---|---|---|---|
| All 22 queries | **4.5 s** | 56.1 s | **3.5 s** |
| Fastest and slowest query | 0.06 and 0.42 s | 0.69 and 5.6 s | 0.03 and 0.40 s |
| Per query against Spark | 5 to 19 times faster (median 13.6) | 1 | |

That is about 12 times faster than Spark on this machine (round 7 measured 5.9 s against 58.5 to
65.2 s). Pondra loaded the files into its lake first (16 s); DuckDB read the Parquet files as they
are. The gates' own TPC-H run puts Pondra level with DuckDB on files (3.31 s against 3.42 s) and
behind DuckDB's own tables from memory (2.11 s against 1.68 s). Flink couldn't take part: PyFlink
has no Parquet reader in this setup.

### Batch: 20 million rows, write then six queries

Seconds, first run of Pondra, uncached.

| | Pondra | Spark | Flink ¹ |
|---|---|---|---|
| Generate and write 20 M rows | **3.3** (Parquet, ZSTD) | 7.3 | 10.5 |
| Q1: `count`, `sum`, `avg` | **0.05** | 0.70 | 5.2 |
| Q2: filter, group by 1,000 | **0.14** | 0.93 | 6.5 |
| Q3: group by 1 M users, top 10 | **0.59** | 2.20 | 8.9 |
| Q4: `count(DISTINCT user)` | **0.51** | 1.75 | 7.5 |
| Q5: join with a dimension | **0.26** | 2.30 | 9.4 |
| Q6: time buckets | **0.25** | 0.52 | 4.7 |
| Peak memory | **293 MB** | 1.5 GB | 3.1 GB |

¹ Flink wrote and read CSV, because no Parquet format jar was available, so its batch numbers are
pessimistic.

Asked a second time, each of these queries returns in about 1 ms from the result cache, until the table
changes.

## Streaming

10 million events, on the same machine.

| Workload | Pondra | Spark Structured Streaming | Flink |
|---|---|---|---|
| Keyed running aggregation (100,000 keys) | 4.2 s end to end (2.4 M/s): over HTTP, stored durably, aggregated by a view, queryable | **3.9 s**, from an in-memory backlog, `noop` sink | 13.3 s (0.75 M/s), in-memory source, `blackhole` sink |
| Stateless ETL (project and filter) | 4.1 s end to end (2.4 M/s), output durable | 5.2 s, `noop` sink | **4.0 s**, `blackhole` sink |

Spark and Flink generated their input in memory and threw their output away. Pondra took its input over
HTTP and committed the results durably, so this comparison is tilted against Pondra. Spark was still
faster on the keyed aggregation, and Flink on stateless ETL.

More streaming numbers:

- **Sustained:** 60 seconds, durable, 8 producers, one node: 2.7 million events a second, and an event
  was visible in the aggregate 0.23 s after its acknowledgement (median). Spark and Flink need Kafka or
  Fluss and checkpoints to do this, so they weren't run on it.
- **A 3-node cluster,** producers writing to the followers: 4.3 to 4.6 million events a second, durable
  and exactly-once. The leader used 26 to 28% of the CPU.
- **Nexmark** (queries q1, q2, q5, q7, q11, over 10 million bids, measured again on 2026-10-02 on
  the 4-core machine): Pondra took 7.1 s for all five over one stream and Flink 2.3 16.2 s (Flink's
  6.6 s to start not counted). Pondra took the bids over HTTP (5.5 s of the 7.1) and wrote every
  view to the lake, and its answers equal DuckDB's; Flink generated the bids in its own process,
  into blackhole sinks. On 2 vCPUs, the day before, it was 14.3 s against 30.4 s.
- **A flow** (views following views, [Flows](/pondra/guides/flows/)): 4 producers, 1,000-row
  batches over HTTP: no view 183,000 rows a second; a filter with two expectations 156,000; then an
  aggregate of it 135,000; then a rollup of that 131,000. At every acknowledgement each stage already
  has the rows: a flow is one commit.

Flink has timers, CEP, Top-N and very large keyed state that Pondra doesn't. See
[Pondra compared](/pondra/concepts/compared/).

Measured again on 2026-10-02 on the 4-core machine (the leader, 8 clients): `/lookup` 38,900 a second
(0.18 ms median), and 27,600 a second (0.22 ms) while a writer upserts 200 rows every few
milliseconds, where it had been 1,700 (4.6 ms): a table's log tail is now indexed by key, so a
lookup no longer reads every segment since the last tiering round. SQL point queries 13,100 a
second. The same dashboard while writes land: 175 a second, 17,400 with `stale_ms=1000`.

Databricks' Lakehouse//RT publishes "as low as 10 ms on smaller datasets" and "sub-100 millisecond
latency at 12,000 queries per second on standard analytical benchmarks", read-only, in beta. Pondra is
ahead on point reads, repeated dashboards and freshness: it serves rows milliseconds old, and it takes
the writes itself. Lakehouse//RT is ahead on new, heavy analytical queries at high concurrency, which it
claims to do on a cluster in under 100 ms. Pondra runs a new TPC-H query in 60 to 600 ms on two cores.

## Small on disk and in memory

Measured on 2026-10-02 (`tools/bench/footprint.py`, two runs, on the 4-core machine): each engine
started, its first answer, its resident memory two seconds later, and after one query over a million
generated rows.

| | Pondra (a server) | DuckDB (in Python) | Polars (in Python) | Spark 4.2 (`local[2]`) | Flink 2.3 (MiniCluster) |
|---|---|---|---|---|---|
| What you install | one binary, 118 MB on Linux (every door, TLS, the console) | 59 MB | 181 MB | 464 MB, and a JVM | 351 MB, and a JVM |
| Start to first answer | 0.12 to 0.14 s | **0.08 s** | 0.12 s | 6.8 to 6.9 s | 6.1 to 6.4 s |
| Idle memory | 104 to 109 MB: about 56 MB its own, 51 MB its binary's code mapped from disk | 50 MB, Python's included | 43 MB | 538 to 549 MB | 585 to 594 MB |
| After the query | 106 to 109 MB | 51 MB | 61 MB | 567 to 573 MB | 744 to 746 MB |

Most of a node's own idle memory is its allocator's huge pages: turned off
(`MIMALLOC_ARENA_EAGER_COMMIT=0`), it is 12 MB, but ClickBench from memory ran 9% slower and
TPC-H 3%, so they stay on.

DuckDB and Polars run inside your process and are the smaller ones; Pondra is a server (with a log,
a catalog, a lake and eight doors), and starts as fast as they do. The JVM engines take seconds to
start and half a gigabyte to idle. In the batch and streaming runs above Pondra peaked at 293 to
609 MB (1.3 GB at 2.7 M events a second sustained), Spark at 0.7 to 1.5 GB, Flink at 1.2 to 3.1 GB.

Memory under saturation is bounded by how many rows may wait in the log for tiering (`--backlog`,
10 million rows by default). One node, 8 producers, 60 seconds, a 100,000-key aggregating view:

| `--backlog` | Throughput | Acknowledged to visible in the view (median / p99) | Peak memory |
|---|---|---|---|
| 10 M (default) | 2.84 M events a second | 205 ms / 730 ms | 1.8 GB |
| 2 M | 784,000 events a second | 49 ms / 234 ms | 1.4 GB |
| 500,000 | 33,000 events a second | 18 ms / 36 ms | 0.35 GB |

Lower it for less memory and lower latency. Raise it to absorb longer bursts. Queries have their own
budget, `--memory-gb` (a third of the machine's memory by default), and sorts, aggregations and joins
that need more spill to disk.

## More than one machine

<Aside type="caution">
This is the part with the least evidence. Pondra has been tested as several processes on one machine,
and on three and six GitHub-hosted machines joined over the public internet. Nothing has run on a
cluster in one data centre yet.
</Aside>

- **On one machine, simulated R2:** where I/O latency dominates, 3 nodes ran 8 of 9 queries 1.2 to 4.3
  times faster than one.
- **Three GitHub runners over the public internet** (TPC-H SF10, links of 17 to 54 ms and 51 to 150
  MB/s): every answer equal to one node's, but a cluster that spread every query took 46.6 s against 23.1
  s for one node, because the shuffles cost about 15 ms per MB moved.
- **Since then, a query spreads only when it pays.** It compares what its plan would move, at the
  measured speed of the slowest link, with the time it would save. On the next runs:

  | | One node | As the cluster decides | Spread anyway |
  |---|---|---|---|
  | Round 19's run | 15.7 s | 18.0 s (5 queries spread) | 39.5 s |
  | Round 21's run | 21.7 s | 21.5 s (3 queries spread, 9 MB moved) | 38.9 s |
  | 0.24.0, 3 nodes | 23.8 s | 24.1 s (7 queries spread) | 49.5 s |
  | 0.24.0, 6 nodes | 24.9 s | 22.4 s (6 queries spread) | 29.0 s |

- **Six nodes** (GitHub runners with 4 vCPUs each, links of 32 to 54 ms and 52 to 89 MB/s): the
  cluster ran TPC-H 10% faster than one node, with every answer the same. The queries it spread got
  faster: q21 took 1.30 s instead of 2.95 s, q19 0.65 s instead of 1.00 s, and q6 0.26 s instead of
  0.57 s. Spreading every query was slower overall (29.0 s), because the slow links make the small
  queries pay more than they gain.
- **What the cluster missed:** spread anyway, q1 took 1.04 s instead of 2.69 s, q3 0.47 s instead of
  0.90 s, and q12 0.36 s instead of 0.87 s, but the cluster kept them on one node. It had estimated the
  rows their aggregations move by the rows they read, not by the few groups they send. 0.26 estimates
  them by their groups, and the next run will show it.

  A cluster on the public internet is a hard case for spreading: its links take 30 to 50 ms and carry
  under 100 MB/s, where a data centre's take under a millisecond and carry 1 GB/s or more.

## Other numbers

- **`cluster_by`:** with 8 million rows and 100,000 users on local disk, a query for one user ran 6.4
  times faster and a range 11 times faster. A full scan ran at 0.6 times the speed.
- **Two `cluster_by` columns** (Hilbert order), 4 million rows from Parquet: a filter on the second
  column took 11.4 ms, against 21.9 ms unclustered and 23.3 ms sorted by the first column alone.
- **A table of a million files** commits an entry of about 20 KB. A query over today skips 1,000,006 of
  them in 12.9 ms.
- **Tiering 8 million rows** takes 1.10 to 1.16 s. A bulk `INSERT` of 6 million rows from `pondra sql`
  takes 1.3 s.
- **A frame is one SQL statement:** over 10 million rows, 0.063 s against 0.065 s for the same SQL
  written by hand.
- **Python functions,** over 1 million rows: 15 million rows a second vectorized and 6.6 million rows a
  second per row. A warm `CALL` of a Python procedure takes 2.4 ms over HTTP.
- **SQL conformance:** 16,646 of 24,783 records (67.2%) of DataFusion's own sqllogictest pass through
  Pondra on one node.

## Measure it yourself

Time your own data and your own hardware. Make a table with 2 million rows:

```sql
CREATE TABLE trips (id BIGINT, zone BIGINT, fare DOUBLE);
INSERT INTO trips SELECT x AS id, x % 500 AS zone, (x % 97) * 0.5 AS fare FROM generate_series(1, 2000000) t(x);
```

Then time a query. Ask it twice: the second answer comes from the result cache, until the table
changes. For a fair time, change the query each time, as this does with `id > n`:

```python
import time
import pondra

db = pondra.connect("http://localhost:8080")

def milliseconds(sql):
    start = time.perf_counter()
    db.sql(sql).rows()
    return (time.perf_counter() - start) * 1000

query = "SELECT zone, sum(fare) AS total FROM trips WHERE id > {n} GROUP BY zone ORDER BY total DESC LIMIT 5"
print(f"a new query:  {milliseconds(query.format(n=1)):7.1f} ms")
print(f"a new query:  {milliseconds(query.format(n=2)):7.1f} ms")
print(f"asked again:  {milliseconds(query.format(n=2)):7.1f} ms  (result cache)")
```

Write speed is the time to an acknowledgement. Lookups need a keyed table:

```python
import statistics

db.sql("CREATE TABLE pings (n BIGINT)")
db.sql("CREATE TABLE accounts (id BIGINT PRIMARY KEY, balance BIGINT)")
db.sql("INSERT INTO accounts SELECT x AS id, 0 AS balance FROM generate_series(1, 100000) t(x)")
db.sql("CHECKPOINT")

def median_ms(work, times=200):
    samples = []
    for n in range(1, times + 1):
        start = time.perf_counter()
        work(n)
        samples.append((time.perf_counter() - start) * 1000)
    return statistics.median(samples)

ack = median_ms(lambda n: db.append("pings", [{"n": n}]))
lookup = median_ms(lambda n: db.lookup("accounts", n))
print(f"append acknowledged: {ack:.2f} ms median")
print(f"key lookup:          {lookup:.2f} ms median")
```

A node counts what it does. `pondra_object_requests_total` counts the writes, lists and deletes the
lake's store was asked for, which is what a bucket bills:

```bash
curl -s localhost:8080/metrics | grep -E '^pondra_(queries_total|rows_in_total|object_requests_total)'
```

`EXPLAIN` shows a query's plan, and whether it spreads over the nodes:

```sql
EXPLAIN SELECT zone, sum(fare) FROM trips GROUP BY zone;
```

```bash norun

```
