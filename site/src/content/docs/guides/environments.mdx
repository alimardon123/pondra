A branch is a whole database that starts as another one is right now, with every table, view,
function and file, without copying any data. Make one per developer, per pull request or for a test
run, change it as you like, compare it with where it came from, and drop it when you're done. What
each database should hold, as files, is in [Projects](/pondra/guides/projects/).

## Make a branch

Say production is this node's lake. A lake is named after its folder; here it is called `lake`:

```sql
CREATE TABLE orders (id BIGINT, amount DOUBLE);
INSERT INTO orders VALUES (1, 10.0), (2, 20.0), (3, 30.0);
CREATE MATERIALIZED VIEW big AS SELECT id, amount FROM orders WHERE amount >= 20;
```

`CREATE DATABASE … CLONE` makes `dev` from it:

```sql
CREATE DATABASE dev CLONE lake;
SELECT * FROM dev.orders ORDER BY id;
```

```text
id | amount
---+-------
 1 |   10.0
 2 |   20.0
 3 |   30.0
```

`dev` lists its base's files where they are, so making it takes about the same time for a table of a
thousand rows or a billion. Only the rows the base hasn't written to files yet, and the workspace's
files, are copied. Rows keep their `_row_id` and `_version`. The database you clone can be this node's
own lake or any database attached to it.

`pondra.databases` shows which database is a branch of which:

<Ways sql={`SELECT name, base, branches FROM pondra.databases ORDER BY name;`} />

```text
name | base | branches
-----+------+---------
dev  | lake |        0
lake |      |        1
```

To take only some schemas, or only the definitions with no rows (for tests that load their own):

```sql
CREATE DATABASE fixtures CLONE lake WITH NO DATA;
SELECT count(*) AS n FROM fixtures.orders;
```

```text
n
-
0
```

`WITH (schemas = (sales, finance))` takes just those schemas.

## Change it apart

Writes to a branch stay in the branch. Its materialized views follow its own rows:

```sql
INSERT INTO dev.orders VALUES (4, 40.0);
UPDATE dev.orders SET amount = 25.0 WHERE id = 2;
```

<Ways sql={`SELECT (SELECT count(*) FROM dev.big) AS in_dev, (SELECT count(*) FROM big) AS here;`} />

```text
in_dev | here
-------+-----
     3 |    2
```

The base carries on too: its merges, compactions and retention never take away a file `dev` reads. It
keeps them for as long as `dev` exists.

## Compare two databases

`pondra.diff('a', 'b')` gives the rows of table `b` that differ from table `a`, in the
[change feed](/pondra/guides/change-rows/)'s words:

<Ways sql={`SELECT _change_type, id, amount FROM pondra.diff('orders', 'dev.orders') ORDER BY id, _change_type;`} />

```text
_change_type     | id | amount
-----------------+----+-------
update_postimage |  2 |   25.0
update_preimage  |  2 |   20.0
insert           |  4 |   40.0
```

Rows both hold alike are matched by their `_row_id` and `_version`, so comparing a big table reads only
its rows, never a join on every column. The command line's
[`pondra diff`](/pondra/guides/projects/#compare-with-another-database) adds the objects that differ.

## Bring tables up to date

A branch stays as its base was when it was made. `ALTER DATABASE … REFRESH` brings tables up to the
base's present, with the materialized views that follow them:

```sql
INSERT INTO orders VALUES (5, 50.0);
ALTER DATABASE dev REFRESH orders;
```

<Ways sql={`SELECT id, amount FROM dev.orders ORDER BY id;`} />

```text
id | amount
---+-------
 1 |   10.0
 2 |   20.0
 3 |   30.0
 5 |   50.0
```

The branch's own changes to those tables go (here row 4 and the update); every other table stays as the
branch has it.

- `ALTER DATABASE dev REFRESH` with no names brings every table the branch took from its base.
- `ALTER DATABASE dev REFRESH orders, customers` brings those, in one commit.
- Naming a materialized view brings the tables it reads, and the view comes with them.

REFRESH says what to do instead of guessing when the branch has a view of those tables that its base
doesn't have, defines one otherwise, or keeps state of its own (a window emitted once, sessions, a
stream join): drop it, refresh, then make it again.

## Drop a branch

```sql
DROP DATABASE fixtures;
DROP DATABASE dev;
```

Only what the branch wrote goes. Its base lets go of the files it kept for it. A database that still has
branches can't be dropped; drop the branches first. A user who isn't an admin drops only the branches it
made.

## What a branch leaves behind

- **Tasks start suspended**, so a branch never runs production's schedules. Resume one with
  `ALTER TASK … RESUME`.
- **Secrets stay with the base.** The one exception is the read-only key that a branch on another server
  keeps to read its base ([below](#production-on-a-server-of-its-own)). A view fed by a Kafka topic
  arrives as a plain table: nothing in a branch reaches outside on its own.
- **A branch is in its base's bucket, or on another server.** In the same bucket it reads the base's
  files and copies none of them. On another server it reads them with that read-only key.

## Branches and environments on a team

On a team, a branch is a Git branch and a database of the same name. The checked-out Git branch picks
the database, and these commands start, switch to and remove them:

```bash norun
pondra branch orders-by-channel          # the Git branch, and its database: prod as it is now
pondra switch fix-vat                    # another branch: git switch, and its database made if it's missing
pondra branch                            # the branches, who made each and when
pondra branch -d orders-by-channel       # its database, and its Git branch once merged
```

- **The database's name** is the branch's name as SQL takes it: lower case, with every character that
  isn't a letter, a digit or `_` made `_`, and a `_` before a name that starts with a digit. So
  `orders-by-channel` is `orders_by_channel`, and `2026-q4` is `_2026_q4`.
- **The checked-out Git branch picks the database.** On `orders-by-channel`, `pondra apply` goes to the
  database `orders_by_channel`. Pondra keeps no state of its own about which branch you are on. On `main`
  there is no branch, so name the environment: `pondra apply test`, `pondra apply prod`. Applying a
  project to a branch is in [Projects](/pondra/guides/projects/#apply-it).
- **A database is made when a command first needs it.** A branch, and test, start as a clone of prod
  (`[env.dev] clone` or `[env.test] clone` in [pondra.toml](/pondra/guides/projects/#pondratoml) names
  another); prod starts empty on its server. Test is then kept, with whatever QA adds to it; `--fresh`
  makes a clone again from where it came from.
- **A branch is its maker's.** `GRANT CLONE ON DATABASE prod TO developers` is all a developer needs to
  make one, and only its maker or an admin drops it. Test and the pull requests' databases are CI's.
  Each project's CI is in [Continuous integration](/pondra/guides/projects/#continuous-integration).
- **A branch's tasks wait to be resumed.** A task made in a branch or in test starts suspended, as the
  tasks it was cloned with do, so nothing in a branch reaches the outside on a schedule. `ALTER TASK name
  RESUME` starts it, and `EXECUTE TASK name` runs it once.
- **A branch reads prod's files gently.** Its reads of prod's objects get a quarter of a node's requests
  at prod's bucket, and halve when the bucket asks to slow down (`pondra_bucket_turns` in `/metrics`), so
  prod's own nodes keep most of it.

### Production on a server of its own

A company that keeps production apart runs it as its own server, with its own bucket, and dev as another.
The commands are the same as on one server; pondra.toml gives each environment its server:

```toml
[env.prod]
server = "https://prod.acme.com"
protected = true

[env.test]
server = "https://test.acme.com"
clone = "prod"

[env.dev]
server = "https://dev.acme.com"      # every branch's database is made here, of prod attached as `prod`
```

Dev's nodes never hold a key that writes production's bucket, yet a branch of production on dev still
copies no data. Dev reads production's files with a key that only reads them, and asks production's
leader to pin the tables it branches, with a token that may do nothing else. [`pondra ci init`](/pondra/guides/projects/#continuous-integration)
makes that token's user on production and prints what to run on each other server, which by hand is:

```sql norun
-- on production
CREATE USER ci_link;
GRANT CLONE ON DATABASE prod TO ci_link;     -- or ON SCHEMA sales: just those
CREATE TOKEN clone FOR USER ci_link;         -- answers the token, once
```

```sql norun
-- on dev (and test)
CREATE SECRET prod_ro (TYPE s3, KEY_ID '…', SECRET '…', REGION 'eu-west-1', SCOPE 's3://acme-prod/prod');
CREATE SECRET prod_clone (TYPE pondra, TOKEN '…', SCOPE 'https://prod.acme.com');
ATTACH 's3://acme-prod/prod' AS prod (READ_ONLY, ENDPOINT 'https://prod.acme.com');
CREATE DATABASE ali CLONE prod;              -- in dev's bucket, no file copied
```

Nothing on dev writes or deletes under production's prefix, whatever dev's own key allows: a write to
`prod` is refused by name. The branch keeps the read-only key in its own catalog, so it reads production
on its own, and `ALTER DATABASE ali REFRESH` asks production's leader again with the branch's own key.
That key reads the branch's own tables and nothing else: no statement in the branch can use it, whoever
owns the branch, so a clone of the `sales` schema can't read `hr`'s files by their URL. A branch can't be
made while production's leader is down; one made earlier can still be read. A clone takes only the
schemas the link's CLONE grant covers (`WITH (schemas = (…))` picks among them).

While dev uses a branch (its own node, or a node it is attached to), it renews its pin in production every
hour with its own key, which dev keeps sealed by its master key. Production lets go of a pin nobody renewed
for 14 days (`PONDRA_PIN_LEASE_SECS`), so a branch whose server is gone stops holding production's files.
Such a branch can then no longer read what production has deleted since: drop it and clone again.

## Projects and Git

A project's files say what each database holds, and `pondra apply` makes them true there: see
[Projects](/pondra/guides/projects/), including protected production. A project kept in the workspace can
be paired with a GitHub branch: see [Git folders](/pondra/guides/git/).
