A branch is a whole database that starts as another one is right now, with every table, view,
function and file, without copying any data. Make one per developer, per pull request or for a test
run, change it as you like, compare it with where it came from, and drop it when you're done.

## Make a branch

Say production is this node's lake. A lake is named after its folder; here it is called `lake`:

```sql
CREATE TABLE orders (id BIGINT, amount DOUBLE);
INSERT INTO orders VALUES (1, 10.0), (2, 20.0), (3, 30.0);
CREATE MATERIALIZED VIEW big AS SELECT id, amount FROM orders WHERE amount >= 20;
```

`CREATE DATABASE … CLONE` makes `dev` from it:

```sql
CREATE DATABASE dev CLONE lake;
SELECT * FROM dev.orders ORDER BY id;
```

```text
id | amount
---+-------
 1 |   10.0
 2 |   20.0
 3 |   30.0
```

`dev` lists its base's files where they are, so making it takes about the same time for a table of a
thousand rows or a billion. Only the rows the base hasn't written to files yet, and the workspace's
files, are copied. Rows keep their `_row_id` and `_version`. The database you clone can be this
node's own lake or any database attached to it.

`pondra.databases` shows which database is a branch of which:

```sql
SELECT name, base, branches FROM pondra.databases ORDER BY name;
```

```text
name | base | branches
-----+------+---------
dev  | lake |        0
lake |      |        1
```

To take only some schemas, or only the definitions with no rows (for tests that load their own):

```sql
CREATE DATABASE fixtures CLONE lake WITH NO DATA;
SELECT count(*) AS n FROM fixtures.orders;
```

```text
n
-
0
```

`WITH (schemas = (sales, finance))` takes just those schemas.

## Change it apart

Writes to a branch stay in the branch. Its materialized views follow its own rows:

```sql
INSERT INTO dev.orders VALUES (4, 40.0);
UPDATE dev.orders SET amount = 25.0 WHERE id = 2;
SELECT (SELECT count(*) FROM dev.big) AS in_dev, (SELECT count(*) FROM big) AS here;
```

```text
in_dev | here
-------+-----
     3 |    2
```

The base carries on too: its merges, compactions and retention never take away a file `dev`
reads. It keeps them for as long as `dev` exists.

## Compare two databases

`pondra.diff('a', 'b')` gives the rows of table `b` that differ from table `a`, in the
[change feed](/pondra/guides/change-rows/)'s words:

```sql
SELECT _change_type, id, amount FROM pondra.diff('orders', 'dev.orders') ORDER BY id, _change_type;
```

```text
_change_type     | id | amount
-----------------+----+-------
update_postimage |  2 |   25.0
update_preimage  |  2 |   20.0
insert           |  4 |   40.0
```

Rows both hold alike are matched by their `_row_id` and `_version`, so comparing a big table reads
only its rows, never a join on every column.

## Bring tables up to date

A branch stays as its base was when it was made. `ALTER DATABASE … REFRESH` brings tables up to the
base's present, with the materialized views that follow them:

```sql
INSERT INTO orders VALUES (5, 50.0);
ALTER DATABASE dev REFRESH orders;
SELECT id, amount FROM dev.orders ORDER BY id;
```

```text
id | amount
---+-------
 1 |   10.0
 2 |   20.0
 3 |   30.0
 5 |   50.0
```

The branch's own changes to those tables go (here row 4 and the update); every other table stays as
the branch has it.

- `ALTER DATABASE dev REFRESH` with no names brings every table the branch took from its base.
- `ALTER DATABASE dev REFRESH orders, customers` brings those, in one commit.
- Naming a materialized view brings the tables it reads, and the view comes with them.

REFRESH says what to do instead of guessing when the branch has a view of those tables that its
base doesn't have, defines one otherwise, or keeps state of its own (a window emitted once,
sessions, a stream join): drop it, refresh, then make it again.

## Drop a branch

```sql
DROP DATABASE fixtures;
DROP DATABASE dev;
```

Only what the branch wrote goes. Its base lets go of the files it kept for it. A database that still
has branches can't be dropped; drop the branches first. A user who isn't an admin drops only the
branches it made.

## What a branch leaves behind

- **Tasks start suspended**, so a branch never runs production's schedules. Resume one with
  `ALTER TASK … RESUME`.
- **Secrets stay with the base**, and a view fed by a Kafka topic arrives as a plain table: nothing
  in a branch reaches outside on its own.
- **A branch lives where its base does**: both in the same bucket, or both on the same machine.

## Apply a project

A project is a folder, usually in Git, that says what every object is. `pondra apply` makes a
database match it, and `pondra plan` shows what that would change first:

- `pondra.toml`: the project's name and its environments;
- `objects/`: `CREATE` statements (tables, views, materialized views, functions, macros, procedures,
  tasks, secrets, roles, sequences, indexes and enum types) and `GRANT`s, in any layout, several to a file;
- `migrations/`: one-off steps, such as a rename or a backfill, each run once in each database, in
  name order, after the objects and columns an apply adds and before what it replaces. A new database
  is made as `objects/` says now, so there they are recorded as run, not run;
- `seeds/`: the rows a new database starts with (`INSERT …`), loaded once when an apply makes it,
  in name order. A branch has its base's rows instead;
- `tests/`: queries; any row one returns is a failure. They run after every apply (`--no-test` skips
  them).

```bash
pondra init shop
cd shop
cat > objects/sales.sql <<'SQL'
CREATE SCHEMA sales;
CREATE TABLE sales.orders (id BIGINT, amount DOUBLE);
CREATE VIEW sales.big AS SELECT * FROM sales.orders WHERE amount >= 20;
SQL
echo "INSERT INTO sales.orders VALUES (1, 10.0), (2, 20.0), (3, 30.0);" > seeds/001-first-orders.sql
echo "SELECT * FROM sales.orders WHERE amount < 0" > tests/no_negative.sql
pondra apply --url http://127.0.0.1:8080
```

```text
a project in shop: pondra.toml, objects/, migrations/, seeds/, tests/
dev: apply 1
  + schema     sales                 made
  + table      sales.orders          made
  + view       sales.big             made
  ▶ seed       001-first-orders.sql  loaded
  ✓ tests      1 passed
  console: http://127.0.0.1:8080/
```

Apply again and nothing changes. Change a file and the plan says how the database will follow it:

```bash
cd shop
cat > objects/sales.sql <<'SQL'
CREATE SCHEMA sales;
CREATE TABLE sales.orders (id BIGINT, amount DOUBLE, channel VARCHAR);
CREATE VIEW sales.big AS SELECT * FROM sales.orders WHERE amount > 20;
SQL
pondra plan --url http://127.0.0.1:8080
```

```text
dev: after apply 1
  ~ table      sales.orders  ADD COLUMN channel VARCHAR
  ~ view       sales.big     replaced
```

- **A table changes in place** only by columns added at the end, types widened and its options. A
  column renamed, dropped or moved is refused with the migration to write
  (`ALTER TABLE … RENAME COLUMN …`): a declaration can't tell a rename from a drop and an add, and an
  apply never loses data unasked. The plan names the views that read the table: the migration drops
  them first, and the apply makes them again after it.
- **Anything else that changed is replaced.** A materialized view is made again from the rows
  already there, with the materialized views that follow it.
- **Drift shows.** An object an apply made and someone changed by hand is listed, and the apply puts
  it back.
- **One apply at a time**, from the plan it showed: if someone applied in between, it is refused, and
  you plan again. Each statement runs under its own part of the apply's job, so running an apply that
  stopped half way again finishes it.
- **Each object has one owner.** An apply changes only what its own project made; another project's
  objects, and objects people made by hand, are left alone. An object the project no longer declares
  is kept unless you apply with `--prune`.

Every apply is a row of `pondra.applies`, with the commit it was of, and its files are kept under
`files/.deploys/`:

```sql
SELECT id, project, status FROM pondra.applies ORDER BY id;
```

```text
id | project | status
---+---------+-------
 1 | shop    | ok
```

A project kept in the workspace applies from SQL too: `CALL plan('shop', env => 'prod')` lists its
plan as rows (`mark`, `change`, `kind`, `name`, `what`; `change` is a word to filter by: `create`,
`alter`, `replace`, `rebuild`, `migrate`, `record` (a migration a new database is marked as having
run), `seed`, `drop`, `keep` or `refuse`), and
`CALL apply('shop', env => 'prod', test => true)` does it.

`pondra export DIR` writes a database's objects as a project's files, so a lake built by hand in the
console becomes a project in one command.

## Branches and environments on a team

On a team, the databases are served by `pondra serve --lakes` (production can run a cluster of its
own), and pondra.toml says where:

```toml
[project]
name = "shop"
server = "https://pondra.acme.com"   # every database here is /db/<name>

[env.prod]
protected = true                     # its objects change only by an apply
values = { min_order = 10 }          # what $min_order is in prod's statements
attach.events = { type = "kafka", url = "kafka://kafka.acme.internal:9092" }

[env.test]
clone = "prod"                       # made from prod once, then applied on each merge

[env.dev]                            # what every branch takes
values = { min_order = 0 }

[secrets]
crm_token = "env:CRM_TOKEN"          # $crm_token, from the applying machine's environment
```

A branch is a Git branch and a database of the same name, made from prod with no file copied. A
developer's day:

```bash norun
pondra login                             # once: a token for each server pondra.toml names, kept in ~/.pondra
pondra branch orders-by-channel          # the Git branch, and its database: prod as it is now
pondra apply                             # the branch's database matches the files, with [env.dev]'s values; tests run
pondra apply --watch                     # or: again on every save
pondra apply local --watch               # or: this laptop's own lake, no server (lake/ in the project)
pondra diff                              # its objects and rows against prod's, as Markdown
pondra switch fix-vat                    # another branch: git switch, and its database made if it's missing
pondra branch                            # the branches, who made each and when
pondra branch -d orders-by-channel       # its database, and its Git branch once merged
```

- **The checked-out Git branch picks the database.** On `orders-by-channel`, `pondra apply` goes to
  the database `orders_by_channel`. Pondra keeps no state of its own about which branch you are on.
  On `main` there is no branch, so name the environment: `pondra apply test`, `pondra apply prod`.
- **A database is made when a command first needs it.** A branch, and test, start as a clone of prod
  (`[env.dev] clone` or `[env.test] clone` names another); prod starts empty on its server. Test is
  then kept, with whatever QA adds to it; `--fresh` makes a clone again from where it came from.
- **A branch is its maker's.** `GRANT CLONE ON DATABASE prod TO developers` is all a developer needs
  to make one, and only its maker or an admin drops it. Test and the pull requests' databases are
  CI's.
- **`--watch` never applies to prod**, to `main` or to a protected database.
- **`pondra apply local` needs no server.** It applies to the lake in the project's `lake/` folder,
  which `pondra` opens as its shell there and `pondra init`'s `.gitignore` leaves out of Git. With
  `--watch` its node stays up, and the console it prints shows each save as it lands.
- **A branch's tasks wait to be resumed.** A task made in a branch or in test starts suspended, as
  the tasks it was cloned with do, so nothing in a branch reaches the outside on a schedule. `ALTER TASK name RESUME` starts it, and `EXECUTE TASK name` runs it once.
- **A branch reads prod's files gently.** Its reads of prod's objects get a quarter of a node's
  requests at prod's bucket, and halve when the bucket asks to slow down
  (`pondra_bucket_turns` in `/metrics`), so prod's own nodes keep most of it.

`pondra ci init` sets up CI for the project in one command. It writes `.github/workflows/pondra.yml`,
in which each pull request's database is made fresh from prod, applied, tested and compared; a merge
applies `main` to test; and prod is applied once someone approves the `prod` environment:

```yaml
- run: pondra apply pr-${{ github.event.number }} --fresh
- run: pondra diff pr-${{ github.event.number }} >> "$GITHUB_STEP_SUMMARY"
```

It also protects prod in pondra.toml, makes the users CI signs in as (`ci`, which may clone prod,
and `ci_prod`, which may only apply to prod) with fresh tokens, and stores them in GitHub through
`gh`, with the `prod` environment reviewed by you. Without `gh` it prints them once. Running it
again rotates the tokens.

```bash norun
pondra ci init
```

### Production on a server of its own

A company that keeps production apart runs it as its own server, with its own bucket, and dev as
another. The commands are the same as on one server; pondra.toml gives each environment its server:

```toml
[env.prod]
server = "https://prod.acme.com"
protected = true

[env.test]
server = "https://test.acme.com"
clone = "prod"

[env.dev]
server = "https://dev.acme.com"      # every branch's database is made here, of prod attached as `prod`
```

Dev's nodes never hold a key that writes production's bucket, yet a branch of production on dev
still copies no data. Dev reads production's files with a key that only reads them, and asks
production's leader to pin the tables it branches, with a token that may do nothing else.
`pondra ci init` makes that token's user on production and prints what to run on each other server,
which by hand is:

```sql norun
-- on production
CREATE USER ci_link;
GRANT CLONE ON DATABASE prod TO ci_link;     -- or ON SCHEMA sales: just those
CREATE TOKEN clone FOR USER ci_link;         -- answers the token, once
```

```sql norun
-- on dev (and test)
CREATE SECRET prod_ro (TYPE s3, KEY_ID '…', SECRET '…', REGION 'eu-west-1', SCOPE 's3://acme-prod/prod');
CREATE SECRET prod_clone (TYPE pondra, TOKEN '…', SCOPE 'https://prod.acme.com');
ATTACH 's3://acme-prod/prod' AS prod (READ_ONLY, ENDPOINT 'https://prod.acme.com');
CREATE DATABASE ali CLONE prod;              -- in dev's bucket, no file copied
```

Nothing on dev writes or deletes under production's prefix, whatever dev's own key allows: a write
to `prod` is refused by name. The branch keeps the read-only key in its own catalog, so it reads
production on its own, and `ALTER DATABASE ali REFRESH` asks production's leader again with the
branch's own key. That key reads the branch's own tables and nothing else: no statement in the
branch can use it, whoever owns the branch, so a clone of the `sales` schema can't read `hr`'s files
by their URL. A branch can't be made while production's leader is down; one made earlier can
still be read. A clone takes only the schemas the link's CLONE grant covers
(`WITH (schemas = (…))` picks among them).

While dev uses a branch (its own node, or a node it is attached to), it renews its pin in production
every hour with its own key, which dev keeps sealed by its master key. Production lets go of a pin
nobody renewed for 14 days (`PONDRA_PIN_LEASE_SECS`), so a branch whose server is gone stops holding
production's files. Such a branch can then no longer read what production has deleted since: drop it
and clone again.

### Protected production

On a protected database, a project's objects change only by an apply. Its objects are what its last
finished apply left: tables, views, roles and grants. A change to one is refused by name, an admin
included, unless an apply makes it. Rows still change, and people still make, change and drop their
own objects, in the project's schema too:

```text
permission denied: table sales.orders is project shop's, and prod is protected: change it in the project and apply it (or an admin lifts the protection: ALTER DATABASE prod SET (protected = false))
```

A user granted APPLY can apply to the database without being an admin, so a CI account needs no
admin token. APPLY is granted on the database alone, not on a schema or a table:

```sql norun
GRANT APPLY ON DATABASE prod TO ci_prod;
```

The project says which environment is protected, and the first apply to it protects the database
once it has finished:

```toml
[env.prod]
protected = true                     # its objects change only by an apply, once one has finished
```

On a protected database an apply needs APPLY or the node's own operator (its tokens and key). A
superuser without APPLY is refused. Lifting the protection is an admin's statement, and it is
audited. It shows in `pondra.databases` until the database is protected again:

```sql norun
ALTER DATABASE prod SET (protected = false);  -- an admin's: written to pondra.audit
ALTER DATABASE prod SET (protected = true);   -- when the fix is in
```

```sql
SELECT name, protected, lifted_at, lifted_by FROM pondra.databases;
```

A branch of a protected database isn't protected: `CREATE DATABASE dev CLONE prod` gives dev a
database whose objects change as dev's own, and prod keeps its protection.
