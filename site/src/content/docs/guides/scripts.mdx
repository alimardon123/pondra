A **variable** holds a value for the statements after it. A **script** is SQL with control flow on
top: branches, loops, error handlers and statements that run at the same time. Use them when a job
has steps that depend on a value from an earlier step. Each statement's syntax is in
[SQL statements](/pondra/sql/statements/#variables).

## Variables

A variable holds one value: a number, text, a date, bytes, a list or a struct (not yet a map). It
belongs to a session, as settings do: a Postgres connection, a client's connection, the shell, or one
script's statements sent together. A procedure and a file run have their own.

```sql
CREATE TABLE daily (day DATE, amount DOUBLE);
INSERT INTO daily VALUES (DATE '2026-09-29', 10), (DATE '2026-09-30', 20);
DECLARE $day DATE = DATE '2026-09-30';
$day = $day - 1;
SELECT $day, sum(amount) AS total FROM daily WHERE day = $day;
```

```text
$day       | total
2026-09-29 | 10.0
```

- **Declare, then set.** `DECLARE $day DATE = …` makes a variable, with its type and value both
  optional. `$day = …` sets it later (`SET $day = …` works too). `RESET $day` forgets it.
- **Worked out once.** The value is computed when it is set and bound wherever `$day` is used. It is
  never pasted into the text: `$day = current_date - 1` is one day for every statement after it.
- **A type holds.** A declared type is applied to each value the variable takes, and a value that
  can't be cast to it is refused.
- **Read it the DuckDB way** with `getvariable('day')`, which is NULL when there is none.
- **Look at them** with `SELECT * FROM pondra.variables`: name, value, type and whether it was declared.
- **A column with no name** that uses a variable is named as written: `$day`, `$day + 1`.
- **`SET name = value`** without a `$` is a session setting, not a variable: see
  [Settings](/pondra/sql/statements/#settings-and-prepared-statements).
- **Where it lives.** A variable belongs to a session or a script. A `DECLARE` sent with no session
  is refused, saying it needs one.
- **Parameters** are variables a caller may set. A file's `DECLARE PARAMETER` is covered in
  [Run files as jobs](/pondra/guides/workspace/#parameters-declared).
- **In Python**, `db.vars.day` is `$day` ([Python client](/pondra/reference/python/)).

## Scripts

A script runs the same from the console, a `.sql` file, `POST /sql`, psql and every Postgres driver,
MCP, the clients' `db.sql`, a SQL procedure and a task. Each statement in it runs as it would on its
own: a query still spreads over the nodes, and a write still goes to the leader.

A first script, with a branch, a loop, a handler and a `SELECT` at the end:

```sql
CREATE TABLE staged (id BIGINT, amount DOUBLE);
INSERT INTO staged VALUES (1, 10), (2, 20), (3, NULL);
DECLARE $missing = (SELECT count(*) FROM staged WHERE amount IS NULL);
IF $missing > 0 THEN
  PRINT 'filling ' || $missing || ' missing amounts';
  UPDATE staged SET amount = 0 WHERE amount IS NULL;
END IF;
DECLARE $total = 0;
FOR r IN (SELECT id, amount FROM staged ORDER BY id) DO
  $total = $total + $r.amount;
END FOR;
BEGIN
  ASSERT $total > 100, 'only ' || $total;
EXCEPTION WHEN assert_failure THEN
  PRINT 'checked: ' || $error;
END;
SELECT $total AS total;
```

```text
total
30.0
```

### Branch and loop

- **Branches** are `IF … THEN … ELSEIF … ELSE … END IF` (`ELSIF` too) and `CASE`, by value or by
  condition: `CASE $x WHEN 1 THEN … END CASE`.
- **Loops** are `WHILE … DO … END WHILE` (while the condition holds), `REPEAT … UNTIL … END REPEAT`
  (until it holds), `LOOP … END LOOP` (until `LEAVE`), and `FOR $r IN (query) DO … END FOR`, which
  gives one row at a time: `$r.column` is its value.
- **`LEAVE label`** ends a loop or a block and **`ITERATE label`** goes on with the next pass, for a
  loop with a label: `outer: WHILE … DO … END WHILE outer`.
- **`END` closes any block.** `END IF`, `END WHILE`, `END FOR`, `END LOOP` and `END CASE` say which
  block they close, and one that names another kind is refused at its line.
- **Conditions and values** are SQL expressions. `EXISTS (SELECT …)` and subqueries work in them.
- **Transactions.** `BEGIN;` and `BEGIN TRANSACTION` still start a transaction. `BEGIN` followed by a
  statement starts a block.
- **`RETURN value`** stops the script, and the value is the script's answer.
- **`PRINT`** writes a notice: the console's Messages, psql's `NOTICE`, the clients' `notices`.

### Handle errors

- **A block** (`BEGIN … EXCEPTION WHEN … THEN … END`) catches the errors its handlers name. A
  block's `DECLARE`s end with it.
- **Names** are Postgres's codes or names: `'40001'`, `serialization_failure`, `division_by_zero`, or
  `OTHERS` (or `SQLEXCEPTION`) for every error.
- **Inside a handler**, `$error` is the message and `$sqlstate` is the code.
- **`RAISE 'text %', $x`** raises an error with code `P0001`, each `%` taking a value. **`RAISE`**
  alone raises the handled error again.
- **`ASSERT cond, 'text'`** raises `P0004` unless the condition holds.

### Build SQL from text

`EXECUTE IMMEDIATE` runs a statement that is made as text, from variables. Its `USING` values are
bound as `$1`, `$2`, … and never pasted into the text. `INTO` puts the first row's values into
variables. `IDENTIFIER(value)` turns a value into a table or column name, where a name goes.

```sql
CREATE TABLE amounts (id BIGINT, amount DOUBLE);
INSERT INTO amounts VALUES (1, 10), (2, 20), (3, 30);
DECLARE $table = 'amounts';
DECLARE $big BIGINT;
EXECUTE IMMEDIATE 'SELECT count(*) FROM ' || $table || ' WHERE amount > $1' INTO $big USING 15;
SELECT $big AS big, (SELECT count(*) FROM IDENTIFIER($table)) AS all_rows;
```

```text
big | all_rows
2   | 3
```

A procedure's answer goes into variables the same way, its first row's values:

```sql
CREATE PROCEDURE biggest() AS BEGIN
  SELECT max(amount) AS top FROM amounts;
END;
CALL biggest() INTO $top;
SELECT $top AS top;
```

```text
top
30.0
```

### Run statements at the same time

A backfill a few passes at a time, and two statements beside each other:

```sql
CREATE TABLE loads (part BIGINT, rows BIGINT);
FOR p IN (SELECT value AS n FROM generate_series(1, 6)) PARALLEL 3 DO
  INSERT INTO loads VALUES ($p.n, (SELECT count(*) FROM staged));
END FOR;
ASYNC INSERT INTO loads VALUES (7, 0);
$last = ASYNC INSERT INTO loads VALUES (8, 0);
AWAIT $last;
AWAIT ALL;
SELECT count(*) AS parts, sum(rows) AS rows FROM loads;
```

```text
parts | rows
8     | 18
```

- **`FOR r IN (query) PARALLEL n DO … END FOR`** runs up to `n` passes at once, from 1 to 64.
- **`ASYNC statement`** starts a statement, or a block, and goes on. **`$h = ASYNC statement`** keeps
  its handle in `$h`.
- **`AWAIT`** waits for every statement started. **`AWAIT $h, …`** waits for the ones named: handles,
  or the run ids of `START CALL`, which wait for a procedure or a file that `START CALL` began from
  any session.
- **Each pass gets a copy of the variables.** What a pass or an `ASYNC` statement sets stays its own,
  so pass results on through tables.
- **A failure stops the loop.** Once a pass fails, no new one starts, and the loop fails with its
  error. `AWAIT $h` fails with that statement's error, and `AWAIT ALL` fails with the first `ASYNC`
  failure's error. A script's end waits for everything it started.
- **Not in a transaction.** `PARALLEL` and `ASYNC` can't run inside `BEGIN … COMMIT`, since their
  passes would share it.
- **`LEAVE` and `RETURN` can't end a `PARALLEL` loop**, since its passes run apart. `ITERATE` ends
  one pass.

### Run again without writing twice

A script run again with the same job (`?job=…` over HTTP, or a task's tick) writes each statement
once, loops, passes and `ASYNC` statements included. A task's graph works the same way: see
[Tasks](/pondra/guides/tasks/).
