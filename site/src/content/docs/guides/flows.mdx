A flow is materialized views following each other: raw rows land in a table (bronze), a view
cleans them (silver), another adds them up (gold). It is what Databricks calls a pipeline (Delta
Live Tables, now Lakeflow) and what you would otherwise run as a chain of jobs. In Pondra every
stage moves **in the same commit** as the rows that started it: when an `INSERT` is acknowledged,
silver and gold already have its rows, and a query never sees one stage ahead of another.

## Bronze, silver, gold

```sql
CREATE TABLE orders (id BIGINT, region VARCHAR, buyer VARCHAR, amount BIGINT, status VARCHAR);
INSERT INTO orders VALUES
  (1, 'eu', 'ann', 30, 'paid'),
  (2, 'eu', 'bob', -5, 'paid'),
  (3, 'us', NULL, 12, 'paid'),
  (4, 'us', 'cat', 50, 'test');
```

Silver keeps the real, paid orders, with two **expectations**: one drops a row that breaks it,
the other keeps the row and counts it.

```sql
CREATE MATERIALIZED VIEW silver (
  CONSTRAINT positive CHECK (amount > 0) ON VIOLATION DROP ROW,
  CONSTRAINT has_buyer EXPECT (buyer IS NOT NULL)
) AS SELECT id, region, buyer, amount FROM orders WHERE status <> 'test';
```

Gold adds silver up, and a third view rolls gold up by region:

```sql
CREATE MATERIALIZED VIEW gold AS
  SELECT region, buyer, count(*) AS orders, sum(amount) AS total FROM silver GROUP BY region, buyer;
CREATE MATERIALIZED VIEW by_region AS
  SELECT region, sum(orders) AS orders, sum(total) AS total FROM gold GROUP BY region;
```

Each view was filled from the rows already there. Now a new order moves through all three in
the commit that writes it:

```sql
INSERT INTO orders VALUES (5, 'eu', 'ann', 20, 'paid');
```

<Ways sql={`SELECT * FROM by_region ORDER BY region`} />

```text
region  orders  total
eu      2       50
us      1       12
```

Order 2 (a negative amount) was dropped by silver's expectation; order 3 (no buyer) was kept and
counted; order 4 is a test and never entered silver.

## Expectations

An expectation is a condition each of a view's rows should meet, checked as the rows are written.
A row breaks it when the condition is false (`NULL` passes, as with a `CHECK` in Postgres).

| You write | A row that breaks it |
|---|---|
| `CONSTRAINT c EXPECT (…)` | is kept, and counted |
| `CONSTRAINT c CHECK (…) ON VIOLATION DROP ROW` (or `EXPECT … ON VIOLATION DROP ROW`) | is left out, and counted |
| `CONSTRAINT c CHECK (…)` (or `… ON VIOLATION FAIL`) | refuses the write that brought it, with Postgres's `check_violation` (23514) |

A refused write is only the writer's: many clients' rows are committed together, and only the
`INSERT` that brought the bad row fails. `pondra.expectations` shows each expectation and how many
rows broke it, counted in the same commits as the rows, so the numbers are exact:

<Ways sql={`SELECT view, expectation, on_violation, failed_rows FROM pondra.expectations ORDER BY expectation`} />

```text
view    expectation  on_violation  failed_rows
silver  has_buyer    keep          1
silver  positive     drop          1
```

```sql
CREATE MATERIALIZED VIEW strict (CONSTRAINT small CHECK (amount < 1000)) AS SELECT id, amount FROM orders;
```

```sql norun
INSERT INTO orders VALUES (6, 'eu', 'ann', 5000, 'paid');
-- ERROR 23514: new row for relation "strict" violates check constraint "small": CHECK (amount < 1000)
```

Expectations go on row-by-row views, not on a view with `GROUP BY`: a grouped view's table keeps
partial sums, not totals, so its totals can't be checked there. Put the expectation on a view of the
same source without `GROUP BY`, and let the grouped view follow that one.

## What a view of a view may be

- **A view of a row-by-row view** (a filter, a projection, a join with another table) takes its
  rows as a view of a table does, and follows their changes: an `UPDATE` or `DELETE` of `orders`
  changes silver's row and then gold's, in one commit.
- **A view of a `GROUP BY` view** sees that view's partial rows (a few per key, combined as you
  read them), not its totals. So it must combine them the same way, a **rollup**: `GROUP BY` some of
  the view's keys, a `WHERE` on those keys only, `sum()` of its sums and counts, `min()` of its
  mins, `max()` of its maxes. Anything else (`SELECT * FROM gold WHERE total > 100`) runs its
  query whole again after each change instead, as `pondra.flows` says
  ([Views kept current](/pondra/guides/views/#anything-else-run-whole)); a stored view
  (`CREATE VIEW`) reads the totals as they are when asked, and costs nothing until then.
- **A view of a view with `avg`, `stddev`, `HAVING` or an expression over its aggregates**, or of a
  history view, runs whole too: such a view works its answers out as it is read, so there are no
  rows to follow.
- A flow is dropped from its end: `DROP MATERIALIZED VIEW silver` is refused while gold
  follows it.

```sql
UPDATE orders SET amount = amount + 10 WHERE id = 1;
```

<Ways sql={`SELECT region, orders, total FROM by_region ORDER BY region`} />

```text
region  orders  total
eu      2       60
us      1       12
```

## Stop a stage, keep its rows

`ALTER MATERIALIZED VIEW v DETACH` stops `v` following its tables and keeps what it holds, as a
table of the same name. From then on it is a table like any other: it takes `INSERT`s, and what
follows it keeps following it. A `GROUP BY` view's table stays a merge table, its rows combining
as they are read, so `UPDATE` and `DELETE` on it are refused (`0A000`). A view that keeps windows is refused, since the windows still open would be
left half counted.

```sql
CREATE MATERIALIZED VIEW eu_orders AS SELECT id, buyer, amount FROM orders WHERE region = 'eu';
ALTER MATERIALIZED VIEW eu_orders DETACH;
INSERT INTO orders VALUES (7, 'eu', 'dee', 40, 'paid');
```

<Ways sql={`SELECT count(*) AS n FROM eu_orders`} />

```text
n
3
```

The order sent after `DETACH` (id 7) isn't in `eu_orders`: only the three eu orders it held.

## History per key (SCD type 2)

A history view keeps every version of each key as it arrives, and gives each its `__start_at` and
`__end_at` when you read it: Databricks' `APPLY CHANGES … STORED AS SCD TYPE 2`, or a slowly
changing dimension of type 2. Versions are put in order by `sequence_by` as they are read, so one
that arrives late still lands in its place, and a version `delete_when` holds for ends its key's
history without being shown.

```sql
CREATE TABLE customer_changes (id BIGINT, name VARCHAR, city VARCHAR, op VARCHAR, at BIGINT);
INSERT INTO customer_changes VALUES (1, 'ann', 'paris', 'U', 1), (1, 'ann', 'rome', 'U', 3), (2, 'bob', 'nyc', 'U', 1);
CREATE MATERIALIZED VIEW customers WITH (history = 'id', sequence_by = 'at', delete_when = 'op = ''D''')
  AS SELECT id, name, city, op, at FROM customer_changes;
INSERT INTO customer_changes VALUES (1, 'ann', 'oslo', 'U', 2), (2, 'bob', NULL, 'D', 5);
```

<Ways sql={`SELECT id, city, __start_at, __end_at FROM customers ORDER BY id, __start_at`} />

```text
id  city   __start_at  __end_at
1   paris  1           2
1   oslo   2           3
1   rome   3
2   nyc    1           5
```

The current version of each key is the one whose `__end_at` is NULL
(`WHERE __end_at IS NULL`). The view's rows are worked out as it is read, so a materialized view
can't follow it; a stored view can.

## The flow

`pondra.flows` lists every materialized view: what it follows, its kind, what else it reads
and its expectations. The console's details panel draws each table's and view's flow, from
its tables to what follows it.

<Ways sql={`SELECT name, follows, kind, expectations FROM pondra.flows ORDER BY name`} />

```text
name       follows           kind       expectations
by_region  gold              aggregate  0
customers  customer_changes  history    0
gold       silver            aggregate  0
silver     orders            rows       2
strict     orders            rows       1
```

<Aside>
A flow commits all its stages in one commit. The node that took the rows in computes each stage as
it packs them, so no stage lags behind the one before it, and there are no checkpoints to keep. The
cost is that every stage's SQL runs as the rows arrive. A view that must see everything at once, such
as a top N over all time or a filter on a total, runs its query whole again after a change instead
([Views kept current](/pondra/guides/views/#anything-else-run-whole)).
</Aside>
