A node told to stop finishes what it is doing first, and a leader hands over at once. That makes an
upgrade simple: replace the nodes one at a time while the cluster keeps serving and taking writes.
A new release opens every older release's lake, and an older release refuses a lake that a newer
one has moved on. [What stays stable](/pondra/reference/stability/) says what every 1.x release keeps working.

## Before you upgrade

<Steps>

1. Read the release notes' **Before you upgrade** for each release you pass, and the table of formats
   below: a release that moves the lake to a newer format is one you can't go back from once it has.
2. For such a release, keep a copy of the lake to go back to. Stop every node (each drains, as below),
   copy the lake's folder or bucket prefix (`cp -a`, `aws s3 sync`, `gsutil -m rsync -r`, `rclone sync`),
   and start the nodes again. A copy taken while nodes run can miss a file a merge replaced meanwhile.
3. Upgrade one node at a time, as the next sections show.

</Steps>

## Upgrading to 0.34

<Aside type="caution" title="Sign-in, from 0.34">

- **A node on the network with no token now asks everyone to sign in.** A node that listens beyond this
  machine (`--addr 0.0.0.0:8080`, a container, a server) used to answer anyone as an admin. Its leader
  now makes the lake's first user, `pondra`, before it serves, and prints its token once on its standard
  error; `pondra token --dir LAKE` makes another, with the node up or down. Before you upgrade such a
  cluster, give every node `--admin-token` (they all need the same one), or read the token from the new
  leader's log. Run `pondra token` once a 0.34 node leads: a 0.33 leader can't record it.
- **With an admin token and no `PONDRA_SECRET_KEY`, the admin token is the master key.** It seals the
  lake's own keys and its secrets, so every node needs the same admin token, as it already did to call
  the others. To change it, start the leader with the new one and the old one in
  `PONDRA_ADMIN_TOKEN_PREVIOUS`: it rewraps what the old one sealed.
- **A node the shell or a `connect()` starts answers only that program**, a token or a signed-in user. Open
  its console from the link the shell prints.
- **A grant on another database** (`GRANT … ON DATABASE`, `GRANT CLONE ON DATABASE prod TO …`) moves the
  lake to format 4, once every node runs 0.34 (a 0.33 node can't read it).

</Aside>

## Which release, which lake format

Every node's `GET /stats` says its release (`version`) and the lake's format (`format`). The leader
also lists the release of every live node (`releases`), which is how you follow an upgrade.

Start two nodes on one lake to try it (any free ports will do):

```bash
mkdir -p upgrade
for i in 1 2; do
  nohup pondra serve upgrade/lake --addr 127.0.0.1:809$i > upgrade/node$i.log 2>&1 &
  echo $! > upgrade/node$i.pid
  sleep 1
done
until curl -sf localhost:8092/ready > /dev/null; do sleep 0.2; done
```

```python
import requests

def stats(port):
    return requests.get(f"http://localhost:{port}/stats", timeout=5).json()

[(stats(port)["role"], stats(port)["version"], stats(port)["format"]) for port in (8091, 8092)]
```

```text
[('leader', '0.33.0', 1), ('follower', '0.33.0', 1)]
```

```python
stats(8091)["releases"]
```

```text
{'127.0.0.1:8091': '0.33.0', '127.0.0.1:8092': '0.33.0'}
```

## Stop a node without dropping work

Send the node `SIGTERM` (what `systemctl stop`, `docker stop` and Kubernetes send), press Ctrl-C, or
close the standard input of a node started with `--stop-with-stdin`. The node then drains:

<Steps>

1. `GET /ready` answers 503, so a load balancer stops sending it work. `GET /healthz` stays 200 for
   as long as the process runs.
2. It waits `PONDRA_DRAIN_GRACE_SECS` (0 by default) for the load balancer to notice.
3. New requests get `503` with `Retry-After: 1`, new Postgres connections are refused, and a new
   statement on a connection already open gets the error `57P01`, so clients try another node.
   Calls between the cluster's own nodes are still answered.
4. Requests that were running when the signal came finish: HTTP requests and Postgres statements,
   for up to `PONDRA_DRAIN_SECS` (30 by default).
5. A leader waits until everything it acknowledged is in the bucket, saves its catalog and steps
   down. Its followers see that and one leads at once, instead of waiting out the 5-second lease that
   a leader that died needs.

</Steps>

A second signal stops the node at once. Kafka and Flight connections end when the process does, and
their clients reconnect to another node as they do when a broker goes.

Stop the leader of the two nodes above and the other leads straight away:

```bash
kill -TERM $(cat upgrade/node1.pid)
until curl -sf localhost:8092/stats | grep -q '"role":"leader"'; do sleep 0.1; done
```

```python
stats(8092)["role"], stats(8092)["term"]
```

```text
('leader', 2)
```

## Health checks

| Endpoint | Answers | Use it for |
|---|---|---|
| `GET /healthz` | 200 while the process runs | liveness: restart the node if it fails |
| `GET /ready` | 200 when the node serves; 503 while it stops, or just after it started and is still catching up with its leader | readiness: send work only while it passes |

Neither needs a token. Give a load balancer a few seconds to notice a node going with
`PONDRA_DRAIN_GRACE_SECS`, and give the process manager longer than `PONDRA_DRAIN_SECS` before it
kills the node (systemd waits 90 s by default, Kubernetes 30 s: set
`terminationGracePeriodSeconds` above the drain).

```bash
curl -s localhost:8092/healthz; echo
curl -s localhost:8092/ready; echo
```

```text
ok
ready
```

## Upgrade a cluster, one node at a time

The cluster keeps serving and taking writes the whole time, with nodes of both releases in it.

<Steps>

1. Back the lake up with the release still running: `BACKUP DATABASE TO 's3://other-bucket/backups/prod'`
   ([backups](/pondra/guides/backups/)). A backup keeps the format it was written at, so the release you
   are leaving can serve it if the upgrade goes wrong.
2. Stop one follower (it drains), replace its binary, and start it again with the same options.
3. Wait until its `GET /ready` answers 200.
4. Do the same for each other follower, and for readers.
5. Last, the leader: it steps down when it stops, and one of the upgraded followers leads at once.
6. Check the leader's `GET /stats`: every node in `releases` says the new release.

</Steps>

On machines of their own that looks like this, however you run the binary:

```bash norun
sudo systemctl stop pondra          # drains, then stops
sudo install pondra-new /usr/local/bin/pondra   # the new release's binary
sudo systemctl start pondra
until curl -sf localhost:8080/ready; do sleep 1; done
```

On one machine, start the stopped node again (the new binary would go here) and wait for it:

```bash
nohup pondra serve upgrade/lake --addr 127.0.0.1:8091 > upgrade/node1.log 2>&1 &
echo $! > upgrade/node1.pid
until curl -sf localhost:8091/ready > /dev/null; do sleep 0.2; done
```

```python
import time

while len(stats(8092)["releases"]) < 2:  # (a node is listed from its first heartbeat)
    time.sleep(0.2)
stats(8091)["role"], sorted(stats(8092)["releases"])
```

```text
('follower', ['127.0.0.1:8091', '127.0.0.1:8092'])
```

The leader can go first too; it only costs the older followers a few seconds more to take over.

## Upgrade each install

A new release replaces the binary. The lake stays where it is, and the node opens it when it starts.

| Installed with | Upgrade | Stay on one release |
|---|---|---|
| pip | `pip install -U pondra` | `pip install 'pondra==0.33.*'` |
| npm | `npm install pondra@latest` | `npm install pondra@0.33` |
| the one-line installer | run it again | set `PONDRA_VERSION=0.33.0` before it (PowerShell: `$env:PONDRA_VERSION = "0.33.0"`) |
| a container | run the new release's tag, `ghcr.io/alimardon123/pondra:0.33.0` | name a tag, never `latest`, for a server |
| Helm | `helm upgrade pondra oci://ghcr.io/alimardon123/charts/pondra --reuse-values --set image.tag=0.33.0` | `image.tag` |
| `pondra service` | upgrade the binary with pip or the installer, then restart the service (below) | keep that binary as it is |

The images and the chart are not in GitHub's registry yet: build the image as the
[deploy guide](/pondra/guides/deploy/) says, and use your own tag.

- **Helm** replaces one pod at a time, and each node drains before it stops: the rolling upgrade
  above, with nothing more to do.
- **Compose:** restart one node at a time, such as `docker compose up -d --no-deps node2`, so the
  cluster always has a leader. A plain `docker compose up -d` restarts every node at once.
- **`pondra service`** runs the binary at the path it was installed from, so the upgraded binary is
  what starts. A restart drains the node first, as any stop does:

  | System | Restart |
  |---|---|
  | Linux | `sudo systemctl restart pondra` (`systemctl --user restart pondra` for your own) |
  | macOS | `sudo launchctl kickstart -k system/pondra` (`launchctl kickstart -k gui/$(id -u)/pondra` for your own) |
  | Windows | `Stop-Service pondra` before the upgrade, since Windows can't replace a running program, and `Start-Service pondra` after it |

  A service installed with `--name` goes by that name instead of `pondra`.

## Which releases can open a lake

A lake has a format, a number in its catalog. A release opens every lake of its format or older:
each release's tests open a lake made by every release since 0.22 and check every answer is the
same. A lake moves to a newer format only when something written in it needs one, and only once
every live node runs a release that knows it, so a mixed cluster never meets a lake one of its nodes
can't read. Until something moves it, the release before still opens it.

| Format | Since | What moves a lake to it |
|---|---|---|
| 1 | 0.32 | every lake, as soon as a release that knows formats opens it |
| 2 | 0.33 | a materialized view that works its answers out as it is read (`avg`, `stddev`, `HAVING`, …) |
| 3 | 0.34 | a lake's own keys sealed by a master key every node shares (`PONDRA_SECRET_KEY`, `PONDRA_KMS_COMMAND`, or the admin token when neither is set): from the first write in a lake the release makes, otherwise by its leader once every node knows format 3 |
| 4 | 0.34 | a grant on another database (`GRANT … ON DATABASE`, `GRANT CLONE ON DATABASE`), which a node of 0.33 can't read: made only once every node knows format 4 |
| 5 | 0.35 | an identity provider (`CREATE IDENTITY PROVIDER`), which a node of 0.34 would ignore: made only once every node knows format 5 |

An older release refuses a newer lake by name, before it reads anything. The message has this shape,
with the lake, its format and the release that wrote it filled in:

```text
<lake> is a lake of format <n>, written by Pondra <release>; this is Pondra <this release>, which knows formats up to <m>: run Pondra <release> or newer here
```

So you can go back to the older release during an upgrade, but not once the lake has moved on.

<Aside type="caution">
Releases 0.30 and older don't know about formats, so they can't refuse a newer lake: don't start one
on a lake a newer release has written. Kafka consumer groups whose offsets were saved by 0.26 or
older start again from their reset policy after an upgrade (offsets are numbered differently since
0.27).
</Aside>

```bash
kill $(cat upgrade/node1.pid upgrade/node2.pid)
```
