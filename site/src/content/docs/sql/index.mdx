Pondra's SQL is [Apache DataFusion](https://datafusion.apache.org/user-guide/sql/index.html)'s,
which reads much like Postgres's, with Postgres's own forms for what changes data (`UPDATE … FROM`,
`INSERT … ON CONFLICT`, `COPY`, `CREATE FUNCTION`, `BEGIN … COMMIT`). DuckDB's spellings work too
(`FROM t` on its own, `PIVOT`, `COLUMNS(…)`, `SUMMARIZE`, lambdas), and Spark's inside
`spark_sql('…')`. A statement means the same through every door: the shell, the console, a notebook's
`%%sql` cell, Python's and JavaScript's `db.sql`, psql, HTTP and MCP.

```sql
CREATE TABLE langs (name VARCHAR, year INT);
INSERT INTO langs VALUES ('SQL', 1974), ('Python', 1991), ('Rust', 2010);
FROM langs WHERE year > 1980 ORDER BY year;
```

DuckDB scripts that begin with `INSTALL` and `LOAD` run as they are for the extensions Pondra has
built in: `httpfs`, `parquet`, `json`, `icu`, `iceberg`, `delta` and `aws`. Pondra has nothing to
install for them, so each statement answers with a notice (`httpfs is built into Pondra: nothing to
install`) and does nothing else. Their limits: `httpfs` reads `s3://` files, and `http(s)://` files
only when a secret covers the URL (`CREATE SECRET … TYPE http`); `json` reads newline-delimited JSON,
not JSON arrays; `icu` gives `SET TimeZone` and `AT TIME ZONE`, not `timezone()`; `aws` reads `s3://`
files with the AWS credential chain. `FORCE INSTALL` and `INSTALL … FROM core` are read the same way.
Any other DuckDB name is refused by name with SQLSTATE `0A000`, and so is a DuckDB extension file
(`LOAD '…duckdb_extension'`), which is DuckDB's own native code. Pondra's own extensions are
WebAssembly files an admin installs with `INSTALL name FROM 'path or URL'` and lists with
`SHOW EXTENSIONS` ([files and secrets](/pondra/sql/statements/#files-and-secrets), ADR-075).
